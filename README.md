# FixRepro

FixRepro replays the same security test against vulnerable and patched robotics or IoT builds, captures hash-verified evidence, and proves the fix without breaking legitimate behavior.

[![CI](https://github.com/ibondarenko1/fixrepro/actions/workflows/ci.yml/badge.svg)](https://github.com/ibondarenko1/fixrepro/actions/workflows/ci.yml)

![FixRepro dashboard showing PATCH VERIFIED and the three required scenarios](docs/submission/screenshots/01-dashboard-overview.png)

*The verified demo shows the unsafe baseline, rejection of the exact same input, and a successful trusted positive control.*

## Why FixRepro

A patch is not proven by a code change alone. FixRepro replays the exact same unsafe input before and after the patch, confirms that legitimate behavior still works, and publishes independently verifiable, tamper-evident evidence.

## Problem

Security patches for connected systems are often accepted as code changes without repeatable proof that unsafe behavior is gone and legitimate behavior still works.

## Implemented Phase 4 product

FixRepro is a deterministic, localhost-only OTA patch-verification product with a judge-facing Web dashboard and Control API. The page loads a verified demonstration bundle immediately, can start one real local verification in the background, presents the three recorded scenarios, proves exact same-input replay, and serves four reverified evidence artifacts.

The interface presents evidence generated by the existing Verification orchestrator. It never calculates, reinterprets, or overrides a verdict.

## Result contract

1. **Vulnerable baseline:** an integrity-valid package signed by an untrusted key is accepted. The Virtual device changes from `1.0.0` to `9.9.0-test`, reproducing unsafe behavior.
2. **Patched security test:** the exact same untrusted package bytes are replayed. The Patched gateway rejects them and the device remains at `1.0.0`.
3. **Positive control:** a trusted package is accepted. The device changes from `1.0.0` to `1.1.0`, proving that legitimate behavior remains available.

`PATCH_VERIFIED` requires all three observations, matching complete envelope and request-body hashes for the first two scenarios, and no operational error. `PATCH_NOT_VERIFIED` means complete deterministic evidence shows a regression. `INCONCLUSIVE` means the baseline, reset, same-input, service, or evidence requirements do not support a safe conclusion.

No language model or probabilistic system determines a verdict.

## Local setup

Python 3.12 or newer is required. Install only into a repository-local virtual environment.

### Windows PowerShell

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[dev]"
```

If Python 3.12 is unavailable, another supported newer interpreter such as `py -3.13` may be used.

### Linux or macOS

```bash
python3.12 -m venv .venv
./.venv/bin/python -m pip install -e '.[dev]'
```

## Run the dashboard locally

Windows:

```powershell
.\.venv\Scripts\python.exe scripts\run_dashboard.py
```

Linux or macOS:

```bash
./.venv/bin/python scripts/run_dashboard.py
```

Open `http://127.0.0.1:8000`. The dashboard binds to loopback by default and must not be exposed as a production service. Its intentionally unauthenticated simulator endpoints are not production interfaces.

The page independently verifies and loads `evidence/demo-bundle` on startup. Selecting **Run live verification** starts exactly one fixed background run under ignored `evidence/runs`; the browser cannot provide a target, path, package, key, command, case, or output directory.

## Run with Docker Compose

```powershell
docker compose up --build
```

Compose publishes only `127.0.0.1:8000:8000`. The Virtual device, Vulnerable gateway, and Patched gateway remain loopback child processes inside one non-root container; their ports are not published. Live output is ephemeral inside the container.

See [docs/DOCKER.md](docs/DOCKER.md) for build, health, smoke, and shutdown commands.

## Dashboard API

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/health` | Dashboard liveness only |
| `GET` | `/api/v1/demo` | Reverify and present the tracked demo bundle |
| `POST` | `/api/v1/verifications` | Start the fixed verification with `{}` and the required action header |
| `GET` | `/api/v1/verifications/{job_id}` | Read an in-memory job state |
| `GET` | `/api/v1/bundles/{bundle_id}/report` | Open the verified HTML report |
| `GET` | `/api/v1/bundles/{bundle_id}/evidence` | Read verified evidence JSON |
| `GET` | `/api/v1/bundles/{bundle_id}/manifest` | Read the verified manifest JSON |
| `GET` | `/api/v1/bundles/{bundle_id}/digest` | Read the verified manifest digest |

Artifact routes resolve only opaque IDs in an internal bundle registry and re-run Bundle verification before every response. Package JSON, public keys, raw records, and logs are not served.

## CLI verification

```powershell
.\.venv\Scripts\python.exe scripts\run_verification.py
.\.venv\Scripts\python.exe scripts\verify_bundle.py evidence\demo-bundle
```

The tracked [HTML report](evidence/demo-bundle/report.html) and `evidence.json` remain covered by the published manifest. Private Ed25519 keys are generated in memory and never written to disk.

## Evidence bundle

```text
evidence/demo-bundle/
  evidence.json
  report.html
  manifest.json
  manifest.sha256
  packages/
  raw/
  trust/trusted-public-key.pem
  run.log
```

`manifest.json` covers every final bundle file except itself and `manifest.sha256`. The separate SHA-256 in `manifest.sha256` is the bundle root digest. The dashboard creates its safe artifact URLs at presentation time and does not modify the bundle.

The bundle is tamper-evident when its published manifest digest is retained separately. This does not replace an externally trusted signature or independent laboratory validation.

## Safety boundaries

This controlled demonstration uses only synthetic packages, keys, services, and builds. It excludes real vendor firmware, private disclosure material, credentials, persistent private signing keys, production targets, and external scanning. All local listeners bind to `127.0.0.1`; container mode widens only the dashboard bind inside the container while Compose limits the host publication to loopback.

The dashboard has no authentication because it is not a production interface. It has no CORS support, cookies, analytics, database, browser storage, uploads, arbitrary targets, or external frontend dependency.

## Limitations

FixRepro proves only that the defined signer-trust regression behaved as recorded under the tested conditions. It does not prove that every vulnerability is fixed or that a build is generally secure. Hardware integration, persistent device state, fleet management, production key management, and cloud deployment are outside this phase.
